# Generating entities

A database that already exists has its schema written down as DDL: the
`CREATE TABLE` and `CREATE TYPE` statements that make it. In Rust,
`pgorm-codegen` reads that DDL and writes the entity modules that describe
it, one file per table. It is a library with no command-line tool: a build
script or a small binary calls it and writes the files where the program
keeps its entities. It reads the DDL with libpg_query, PostgreSQL's own
parser, as PostgreSQL 18 reads it, and connects to no database.

`pgorm.codegen.models_from_sql` brings it to Python. It hands the DDL to
pgorm-codegen, which reads it as it reads it for Rust entities, and returns
the module of [declared models](03-entities.md) that describe it: a `Model`
per table, each relation in both directions, each junction's path, and the
[disjoint](15-disjoint.md) and [one-of](16-one-of.md) models, laid out as
black lays out Python, so nothing needs to run over it once it is written.

A Python program can also take Rust's own route, and generate Rust entities
to [register](24-registrations.md) in an application wheel of its own:

1. pgorm-codegen reads the DDL and writes the Rust entities of a crate of
   their own.
2. `pgorm.codegen` registers that crate's entities into an application wheel
   and generates `CakeModel`, `CakeActive` and `Cake` for each.

This chapter follows the Rust chapter, saying at each step what the Rust
tool does and what it means for the Python side. [The Rust guide's
Generating entities](../../docs/guide/22-codegen.md) has every detail of
pgorm-codegen itself.

## From DDL to declared models

`models_from_sql` takes the DDL text and returns the module's source, for the
program to write beside its code. Here the bakery's own tables are read back,
from the DDL its models write:

```python
from pgorm.codegen import models_from_sql

import bakery

ddl = "".join(statement.inspect().sql + ";\n" for statement in bakery.statements())
source = models_from_sql(ddl)

assert source.startswith('"""Declared models of a schema\'s tables, @generated by pgorm-codegen')
assert 'FLAVOR = TypeName("flavor", schema="public")' in source
assert """Cake = Model(
    "cake",
    {
        "id": Column("i32", primary_key=True, auto_increment=True),
        "name": Column("text", column_type="varchar"),
        "flavor": Column(FLAVOR, values=["chocolate", "vanilla", "lemon", "carrot"]),
        "price": Column(
            "decimal", column_type=s.DataType("numeric", precision=10, scale=2)
        ),
        "gluten_free": Column("bool"),
        "bakery_id": Column("i32"),
    },
)""" in source
assert 'cake_bakery = Cake.belongs_to(Bakery, from_="bakery_id", to="id")' in source
assert "cake_related_baker = Cake.related(cake_baker_baker, via=cake_cake_baker)" in source
```

The module is ordinary Python: written to a file, it imports, its models
read the tables the DDL creates, and strict mypy checks it as it checks
models written by hand. Here it is written and imported, and its cake model
reads the bakery's cakes:

```python
import asyncio
import importlib.util
import os
from pathlib import Path
import tempfile

from pgorm import Pool
from pgorm.codegen import models_from_sql

import bakery

ddl = "".join(statement.inspect().sql + ";\n" for statement in bakery.statements())


async def main() -> None:
    with tempfile.TemporaryDirectory() as directory:
        path = Path(directory) / "bakery_models.py"
        path.write_text(models_from_sql(ddl))
        spec = importlib.util.spec_from_file_location("bakery_models", path)
        assert spec is not None and spec.loader is not None
        models = importlib.util.module_from_spec(spec)
        spec.loader.exec_module(models)

    async with Pool(os.environ["DATABASE_URL"]) as pool:
        lemon = await models.Cake.find().where(models.Cake.col("flavor") == "lemon").all(pool)
        assert [cake["name"] for cake in lemon] == ["Lemon Drizzle"]
        adas = await models.Cake.find().join(models.cake_cake_baker).join(
            models.cake_baker_baker
        ).where(models.Baker.col("name") == "Ada").order_by(models.Cake.col("id").asc()).all(pool)
        assert [cake["name"] for cake in adas] == ["Chocolate Fudge", "Lemon Drizzle"]


asyncio.run(main())
```

A program writes the module once, when its schema changes, with the
codegen command line:

```sh
python -m pgorm.codegen models schema.sql --output bakery_models.py
```

and then imports it, `from bakery_models import Cake, cake_bakery`.

Each model is named for its table in PascalCase, as the Rust entity is, and
each field for its column. Each relation is the Rust `Relation` enum's
variant it is, named for the model it starts at and the table it reaches: a
foreign key is a `belongs_to` on the table holding it, `cake_bakery`, with
the key's `on_delete` and `on_update`, and the `has_many` or `has_one` of the
table it points to, `bakery_cake`; a junction such as `cake_baker` gives its
two ends a `related` path, `cake_related_baker`. A table's single-column
unique keys and its others are its `unique_keys`. The tables
`Schema::create_disjoint` writes are a `Disjoint` over the base's and the
kinds' models, `PaymentDisjoint` for a base named `payment`, and a one-of
reference's `CHECK` a `OneOf`, `ReviewSubject` for `ck-review-subject`. An
enum, and a range type the schema creates, is a `TypeName` or `CreatedRange`
constant, in `public` where the DDL leaves it unqualified, since a model
names a type's schema; `schema_name=` names another, and puts an
unqualified table in it too. `unkinded_disjoint=` names table sets read as an
unkinded disjoint model, each a dict of its `base`, its `kinds` and its
`unit`, each table a name or a `(schema, name)` pair, as Rust's option does.
[`tests/models_from_sql/models.py`](../tests/models_from_sql/models.py) is
the module written for a schema holding every column type a model takes,
which the suite imports and reads and writes rows through.

Each column takes the kind [Models and entities](03-entities.md) maps its
type to, and states its type with `column_type` wherever the kind's own type
is not it, so the table `pgorm.schema.from_model` writes from the model is
the one the DDL creates:

| Column type | Declared as |
| --- | --- |
| `text` | `Column("text")` |
| `varchar`, `varchar(n)`, `char(n)` | `Column("text", column_type=..)`: `"varchar"`, `s.DataType("varchar", length=n)` |
| `smallint`, `integer`, `bigint` | `Column("i16")`, `Column("i32")`, `Column("i64")` |
| `real`, `double precision` | `Column("f32")`, `Column("f64")` |
| `numeric`, `numeric(p, s)` | `Column("decimal")`, with `s.DataType("numeric", precision=p, scale=s)` |
| `money` | `Column("decimal", column_type="money")` |
| `boolean` | `Column("bool")` |
| `date`, `time`, `timestamp`, `timestamptz` | `Column("date")`, `"time"`, `"datetime"`, `"datetime_utc"` |
| `interval`, with fields | `Column("interval")`, with `s.DataType("interval", fields=..)` |
| `uuid`, `bytea` | `Column("uuid")`, `Column("bytes")` |
| `jsonb`, `json` | `Column("json")`, `json` with `column_type="json"` |
| an enum | its `TypeName` constant, with `values=[..]` |
| a range type the schema creates | its `CreatedRange` or `CreatedMultirange` constant |
| a built-in range | `Column("int4range")` and the others, named as PostgreSQL names them |
| a domain | the kind of the type it is over, with `column_type=s.DataType.domain(name, base)` |
| a nullable column | `nullable=True` |
| an array | `array=True` |
| a `serial` key | `auto_increment=True` |
| an identity column | `generated="always"` or `generated="by_default"` |
| a `DEFAULT` | `default_value=` for a literal, `default_expr=` for an expression such as `current_timestamp()` |
| a generated column | `generated_stored=` or `generated_virtual=`, an expression over `col(..)` |

A domain over an enum is the enum's `TypeName` with the domain as its
`column_type`, which the model compares as the enum ([Values and
types](13-values.md#domains)).

The reading is pgorm-codegen's, so it refuses what the Rust route refuses
([below](#what-it-refuses)), with a `ConstructionError` whose message names
it, and it refuses besides what a model has no word for: a foreign key that
is `DEFERRABLE`, `NOT ENFORCED` or has a `PERIOD`, a `DEFAULT NULL`, a
`bpchar`, or a type named outside the vocabulary. A name only Rust cannot
spell, such as a column named `1st`, is no refusal here: Rust's names are the
Rust writer's to check, and the package carries no Rust writer.

## Adding the crate

The rest of this chapter takes the Rust route, which a program registering
Rust entities follows. There, `pgorm-codegen` lives in pgorm's repository and
is depended on the same way as pgorm. Generation happens when the schema changes, not when the program
runs, so it is a dependency of a small tool of your own, or a
build-dependency:

```toml
[dependencies]
pgorm-codegen = { git = "https://github.com/necessary-nu/pgorm" }
```

## From DDL to entity files

`entities_from_sql` takes the DDL text and an `EntityWriterOptions`, and
returns the files to write, each a `name` and its `content`:

- one `<table>.rs` per table, holding its `Model` and `Relation`;
- `mod.rs`, declaring each module, or `lib.rs` instead when the `lib` option
  is set, for a crate of entities alone;
- `prelude.rs`, which re-exports each `Entity` under the table's name in
  CamelCase;
- `pgorm_active_enums.rs`, one `ActiveEnum` per enum type the tables use;
- `pgorm_range_types.rs`, one `CreatedRange` newtype per range type the
  schema creates.

For a Python application, generate a crate of entities alone, with the `lib`
option, so that the registration build can depend on it. A small binary of
your own, outside that crate, reads the schema and writes the files into
the crate's `src`:

```rust
use pgorm_codegen::{EntityWriterOptions, entities_from_sql};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let ddl = std::fs::read_to_string("schema.sql")?;
    let options = EntityWriterOptions {
        lib: true,
        ..Default::default()
    };
    let output = entities_from_sql(&ddl, options)?;
    let out = std::path::Path::new("bakery-entities/src");
    std::fs::create_dir_all(out)?;
    for file in output.files {
        std::fs::write(out.join(&file.name), file.content)?;
    }
    Ok(())
}
```

The entity crate's `Cargo.toml` depends on pgorm, as any crate of entities
does. Each run writes every file afresh, `lib.rs` and `prelude.rs`
included, so keep hand-written code out of the generated directory. The
files are Rust laid out as [the Rust guide's entities](../../docs/guide/02-entities.md)
are written, so nothing needs to run over them once they are written.

## Writing the DDL from Python

pgorm-codegen reads `CREATE` statements, each table's keys inside it. A
Python program whose models write their own tables, as
[`bakery.py`](bakery.py)'s do through `pgorm.schema.from_model`, already
writes DDL of that shape: render each statement and write them, in order, to
the file the Rust tool reads.

```python
import bakery

ddl = "".join(statement.inspect().sql + ";\n" for statement in bakery.statements())

assert ddl.startswith(
    "CREATE TYPE \"public\".\"flavor\" AS ENUM ('chocolate', 'vanilla', 'lemon', 'carrot');\n"
)
assert (
    'CREATE TABLE "cake" ( "id" serial NOT NULL, "name" varchar NOT NULL, '
    '"flavor" public.flavor NOT NULL, "price" decimal(10, 2) NOT NULL, "gluten_free" bool NOT NULL, '
    '"bakery_id" integer NOT NULL, PRIMARY KEY ("id"), '
    'CONSTRAINT "fk-cake-bakery_id" FOREIGN KEY ("bakery_id") REFERENCES "bakery" ("id") );\n'
) in ddl
assert ddl.count("CREATE TABLE") == 7
```

The cake's statement is the one Rust's schema generation writes for the Rust
guide's cake entity, but for the flavor's type, which a Python model names
with its schema: read back, it is an entity whose enum says
`schema_name = "public"`.

The output of `pg_dump --schema-only` is not that shape: it opens with
`SET`s, changes owners, and adds its keys with `ALTER TABLE` after the
tables, and pgorm-codegen refuses it.

## Options

`EntityWriterOptions` names every option, and its `Default` asks for none.
Most shape only the Rust source: serde derives (`with_serde` and the two
`serde_skip_*` options), `Copy` on enums (`with_copy_enums`), and extra
derives and attributes (`model_extra_derives`, `model_extra_attributes`,
`enum_extra_derives`, `enum_extra_attributes`); a registration reads the
entity's columns and their types, which these leave as they are. `lib`
writes the `lib.rs` a crate of entities needs.
`schema_name` sets the schema an unqualified table is in, which the
registered entity's `describe()` then reports as its `schema`.
`unkinded_disjoint` names table sets to read as an unkinded [disjoint
enum](15-disjoint.md). An option that is not valid Rust is refused before
the schema is read.

## Types

pgorm-codegen gives each column the Rust type [the Rust guide's
Entities](../../docs/guide/02-entities.md) maps it to, and a typed Python
view reads that Rust type as the Python type its values decode as:

| Column | Rust field | Python property |
| --- | --- | --- |
| `varchar`, `text` | `String` | `str` |
| `integer`, `bigint` | `i32`, `i64` | `int` |
| `boolean` | `bool` | `bool` |
| `numeric` | `Decimal` | `Decimal` |
| `date` | `Date` | `date` |
| `timestamptz` | `DateTimeWithTimeZone` | `datetime` |
| `interval` | `Interval` | `pgorm.Interval` |
| `uuid` | `Uuid` | `UUID` |
| an enum type | its `ActiveEnum` | `str` |
| a nullable column | `Option<T>` | `T \| None` |
| an array | `Vec<T>` | `list[T]` |
| a domain | its base's type | its base's type |
| a range | `Range`, or a `CreatedRange` newtype | `Any` |

Where the field's type would not give the column's own type back, the Rust
file states a `column_type`, as for a `numeric(10, 2)`; the registration's
`describe()` reports it as the column's `sql_type`, and its `kind` is what
the column's values bind as. [Registering Rust
entities](24-registrations.md#the-generated-typed-views) lists every Rust
type the views know; a type outside them reads as `Any`.

## What it refuses

pgorm-codegen reads the DDL in full or not at all. It reads what the entity
model can hold: `CREATE TABLE` with its columns, keys, foreign keys, defaults
and generation expressions; `ALTER TABLE` adding a column or a constraint to
a table the text creates; enum and range types; domains; indexes; schemas;
and comments on tables and columns. Anything else, from a `CREATE TRIGGER`
to a `CHECK` on a column, or a column of a type the entity model lacks such
as `point`, is refused with a `TransformError` naming it and the statement
it is in, never skipped. A schema that holds such things keeps them in DDL
of its own, outside the file pgorm-codegen reads.

## From entities and back

Schema generation turns an entity into DDL, and pgorm-codegen turns DDL into
an entity, so each undoes the other. On the Python side,
`pgorm.schema.from_entity` writes a registered Rust entity's DDL
([Registering Rust entities](24-registrations.md#schema-from-a-registered-entity)),
which pgorm-codegen reads back as the same entity. A Python model has the
same pair: `pgorm.schema.from_model` writes its DDL
([Schema generation](14-schema.md)), and `models_from_sql` reads the DDL
back as the model, as the bakery's do above.

## Disjoint enums and one-of references

The tables Rust's `Schema::create_disjoint` writes for a [disjoint
enum](15-disjoint.md) generate as that enum again: the base's module holds
the `#[derive(Disjoint)]` enum beside the base's `Model`, and each kind's
table is an entity of its own. A table's `CHECK` that a [one-of
reference](16-one-of.md) writes generates its `#[derive(OneOf)]` enum the
same way. `pgorm.schema.create_disjoint` writes a Python disjoint model's
tables with the same code, pgorm's `DisjointShape`.

On the Python side, `pgorm.codegen` registers a generated disjoint enum
under `disjoints` and gives it a typed view. It does not describe one-of
enums yet; a wheel that registers one is built by hand.

## The stages

`entities_from_sql` runs three public stages that Rust can call one at a
time: `parse_schema` reads the text into pgorm-query's `CREATE TABLE`
statements, `EntityTransformer::transform` builds the entities from them,
and `EntityWriter::generate` writes the files. `models_from_sql` runs the
first and the neutral half of the second, `EntityTransformer::entities`,
then pgorm-codegen's Python writer, all inside the package; the stages are
not called one at a time from Python.

## From generated entities to Python

Once the entity crate exists, describe its entities in an `application.json`
beside its `Cargo.toml`, with each table's module as its Rust path, the
entity crate being a crate of entities alone:

```json
{
  "schema_version": 1,
  "module": "bakery_entities",
  "entity_crate": ".",
  "entities": [
    {"name": "bakery_entities.Bakery", "rust": "bakery::Entity", "python": "Bakery"},
    {"name": "bakery_entities.Cake", "rust": "cake::Entity", "python": "Cake"}
  ]
}
```

and build it as [Registering Rust
entities](24-registrations.md#building-an-application-wheel-with-pgormcodegen)
describes: scaffold, the probe build, emit, and the final build. The wheel
it installs exports `from pgorm.bakery_entities import Cake, CakeModel,
CakeActive`, typed as the table above says. When the schema changes, run
pgorm-codegen again, then the four steps again.
