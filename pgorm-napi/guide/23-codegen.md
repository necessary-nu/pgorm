# Generating entities

A database that already exists has its schema written down as DDL: the
`CREATE TABLE` and `CREATE TYPE` statements that make it. In Rust,
`pgorm-codegen` reads that DDL and writes the entity modules that describe
it, one file per table, in the form the Rust guide's Entities chapter
teaches. This chapter is the JavaScript dialect of the [Rust guide's
chapter](../../docs/guide/22-codegen.md) of the same name.

`modelsFromSql` brings it to JavaScript. It hands the DDL to pgorm-codegen,
which reads it as it reads it for Rust entities, and returns the TypeScript
module of the [declarations](03-entities.md) that describe it: an exported
`model(..)` per table, each relation in both directions, each junction's
path, and the [disjoint](15-disjoint.md) and [one-of](16-one-of.md) shapes,
laid out as deno fmt lays out TypeScript, so nothing needs to run over it
once it is written. Nothing connects to a database. Here are the bakery's
`bakery` and `cake` tables, with the cake's flavor enum:

```ts
import assert from "node:assert/strict";
import { modelsFromSql } from "@necessary/pgorm";

const ddl = `
CREATE TYPE flavor AS ENUM ('chocolate', 'vanilla', 'lemon', 'carrot');
CREATE TABLE bakery (id serial PRIMARY KEY, name varchar NOT NULL, city varchar NOT NULL);
CREATE TABLE cake (
  id serial PRIMARY KEY,
  name varchar NOT NULL,
  flavor flavor NOT NULL,
  price numeric(10, 2) NOT NULL,
  gluten_free boolean NOT NULL,
  bakery_id integer NOT NULL REFERENCES bakery (id)
);
`;
const source = modelsFromSql(ddl);
assert.ok(source.startsWith("// Declared models of a schema's tables, @generated by pgorm-codegen"));
assert.ok(source.includes(`export const flavor = new TypeName("flavor", { schema: "public" });`));
const cake = [
  `export const Cake = model("cake", {`,
  `  renameAll: "snake_case",`,
  `  columns: {`,
  `    id: column("i32", { primaryKey: true, autoIncrement: true }),`,
  `    name: column("text", { columnType: "varchar" }),`,
  `    flavor: column(flavor, {`,
  `      values: ["chocolate", "vanilla", "lemon", "carrot"],`,
  `    }),`,
  `    price: column("decimal", {`,
  `      columnType: new DataType("numeric", { precision: 10, scale: 2 }),`,
  `    }),`,
  `    glutenFree: column("bool"),`,
  `    bakeryId: column("i32"),`,
  `  },`,
  `});`,
];
assert.ok(source.includes(cake.join("\n")));
assert.ok(source.includes(`export const bakeryCake = Bakery.hasMany(Cake, { from: "id", to: "bakeryId" });`));
const cakeBakery = [
  `export const cakeBakery = Cake.belongsTo(Bakery, {`,
  `  from: "bakeryId",`,
  `  to: "id",`,
  `});`,
];
assert.ok(source.includes(cakeBakery.join("\n")));
```

A program writes the module once, beside its code, and imports its models as
it imports declarations written by hand; the codegen command line writes it
from a file:

```sh
node pgorm-napi/codegen/cli.js models schema.sql --output models.ts
```

Each model is named for its table in PascalCase, as the Rust entity is, and
each field for its column in camelCase, the model saying `renameAll:
"snake_case"` where a field relies on it. Each relation is the Rust
`Relation` enum's variant it is, named for the model it starts at and the
table it reaches: a foreign key is a `belongsTo` on the table holding it,
`cakeBakery`, and the `hasMany` or `hasOne` of the table it points to,
`bakeryCake`, and a junction such as `cake_baker` gives its two ends a
`related` path, `cakeRelatedBaker`. A table's single-column unique keys and
its others are its `uniqueKeys`. The tables `Schema::create_disjoint` writes
are a `disjoint(..)` over the base's and the kinds' models, `PaymentDisjoint`
for a base named `payment`, and a one-of reference's `CHECK` an `oneOf(..)`,
`ReviewSubject` for `ck-review-subject`. An enum, and a range type the schema
creates, is a `TypeName` or `CreatedRange` the module exports, in `public`
where the DDL leaves it unqualified, since a declaration names a type's
schema; the `schemaName` option names another, and puts an unqualified table
in it too. `unkindedDisjoint` names table sets read as an unkinded disjoint
model, each table a name or a `[schema, name]` pair, as Rust's option does.
[`tests/models-from-sql/models.ts`](../tests/models-from-sql/models.ts) is the
module written for a schema holding every column type a declaration takes,
which the suite imports and reads and writes rows through.

The reading is pgorm-codegen's, so it refuses what Rust's does, with a
`ConstructionError` whose message names it, and it refuses besides what a
declaration has no word for: a foreign key that is `DEFERRABLE`, `NOT
ENFORCED` or has a `PERIOD`, a `DEFAULT NULL`, a `bpchar`, or a type named
outside the vocabulary. A name only Rust cannot spell, such as a column named
`1st`, is no refusal here: Rust's names are the Rust writer's to check, and
the addon carries no Rust writer.

## Declarations written by hand

A declaration written by hand, or one the DDL has changed under, declares each
column's kind, and every read checks the result against
the declaration as it decodes: the result's columns are exactly the ones
selected, each of its declared kind, with no NULL where the field is not
nullable and no label an enum field does not list. A declaration that does
not match its table is a `DecodeError` at the first read, never a value read
wrongly. Here the bakery's `order_line` table is declared with its quantity as
an `i64`, where the column is an `integer`:

```ts
import assert from "node:assert/strict";
import { column, DecodeError, model } from "@necessary/pgorm";

const Mistaken = model("order_line", {
  columns: {
    id: column("i32", { primaryKey: true, default: true }),
    orderId: column("i32", { name: "order_id" }),
    cakeId: column("i32", { name: "cake_id" }),
    quantity: column("i64"),
    price: column("decimal"),
  },
});
await assert.rejects(Mistaken.find().all(pool), DecodeError);

// The bakery's own declaration matches the table.
const lines = await OrderLine.find().all(pool);
assert.equal(lines.length, 3);
```

So a test that reads one row of each model, against a database built from
the same DDL the program deploys, holds every declaration to its table, as
Rust's generated entities are held to theirs by being written from it.

`describe()` gives a declaration back as data, the kinds spelt as a result
spells its columns' kinds, which is how such a test can report what it
compared:

```ts
import assert from "node:assert/strict";

const { table, primaryKey, fields } = Cake.describe();
assert.equal(table, "cake");
assert.deepEqual(primaryKey, ["id"]);
assert.equal(fields.glutenFree?.column, "gluten_free");
assert.equal(fields.price?.kind, "decimal");
assert.equal(fields.flavor?.kind, `enum "public"."flavor"`);
```

## Types

`modelsFromSql` declares each column with the kind [Entities](03-entities.md)
maps it to, the other way round, as Rust's generator maps each column to a
field type, and states the column's type with `columnType` wherever the
kind's own type is not it, so the table [`fromModel`](14-schema.md) writes
from the declaration is the one the DDL creates:

| Column type | Declared as |
| --- | --- |
| `text` | `column("text")` |
| `varchar`, `varchar(n)`, `char(n)` | `column("text", { columnType: .. })`: `"varchar"`, `new DataType("varchar", { length: n })` |
| `smallint`, `integer`, `bigint` | `column("i16")`, `column("i32")`, `column("i64")` |
| `real`, `double precision` | `column("f32")`, `column("f64")` |
| `numeric`, `numeric(p, s)` | `column("decimal")`, with `new DataType("numeric", { precision, scale })` |
| `money` | `column("decimal", { columnType: "money" })` |
| `boolean` | `column("bool")` |
| `date`, `time`, `timestamp` | `column("date")`, `column("time")`, `column("datetime")` |
| `timestamptz` | `column("datetime_utc")` |
| `interval`, with fields | `column("interval")`, with `new DataType("interval", { fields })` |
| `uuid`, `bytea` | `column("uuid")`, `column("bytes")` |
| `jsonb`, `json` | `column("json")`, `json` with `columnType: "json"` |
| an enum | its `TypeName`, with `values: [..]` |
| a range type the schema creates | its `CreatedRange` or `CreatedMultirange` |
| a built-in range | `column("int4range")` and the others, named as PostgreSQL names them |
| a domain | the kind of the type it is over, with `columnType: DataType.domain(name, base)` |
| a nullable column | `{ nullable: true }` |
| an array | `{ array: true }` |
| a `serial` key | `{ autoIncrement: true }` |
| an identity column | `{ generated: "always" }` or `{ generated: "byDefault" }` |
| a `DEFAULT` | `defaultValue` for a literal, `defaultExpr` for an expression such as `currentTimestamp()` |
| a generated column | `generatedStored` or `generatedVirtual`, an expression over `col(..)` |

A domain over an enum is the enum's `TypeName` with the domain as its
`columnType`, which the model compares as the enum ([Values and
types](13-values.md)). A foreign key is a relation, `belongsTo` on the table
holding it and `hasMany` or `hasOne` on the table it points to
([Relations](07-relations.md)), with the key's `onDelete` and `onUpdate`.
[Values and types](13-values.md) covers each kind's values.
